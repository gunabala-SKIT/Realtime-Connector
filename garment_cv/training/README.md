# Training pipelines — demo models, not production data

Three datasets live here. Only the third is real footage, and even it is a small single-session
demo, not the varied production-floor data spec section 7 asks for:

1. **Synthetic shapes** (`make_synthetic_dataset.py`) — procedurally drawn geometry, see below.
2. **AI-generated photos** (`prepare_real_dataset.py`) — a small, hand-labeled set of AI-generated
   images of a room that doesn't exist; the model trained on it detected nothing on the real camera.
3. **Real footage from the real camera** (`capture_real_footage.py`, `bootstrap_real_labels.py`,
   `train_live.py`) — see section 3 below.

Neither produces a usable garment-factory detector. Both exist to prove the dataset → fine-tune →
swap-into-`GARMENT_DETECT_MODEL` pipeline genuinely works end to end, before any real training data
exists. Neither model will reliably detect real fabric, tools, or activity in an actual production
environment.

## 1. Synthetic shapes

## Why synthetic, and why that's a real limitation

Spec section 7 is explicit: *"The system must support custom training using real garment-factory
images and videos. Collect training data from the actual production environment."* None exists yet
— that's the whole reason this product runs on a COCO-pretrained stand-in in the first place (see
the main [`README.md`](../README.md), Phase 2). Rather than wait to prove the training pipeline
itself works, `make_synthetic_dataset.py` draws simple, distinct geometric shapes standing in for
the 7 classes with no COCO match:

| Class | Synthetic stand-in |
|---|---|
| `fabric` | a large flat-colored rectangle with a few horizontal "fold" lines |
| `marking_tool` | a small bright thin rectangle |
| `measuring_scale` | a long yellow rectangle with ruler tick marks |
| `pattern` | a pale rectangle with a dashed border |
| `sewing_machine` | a dark block with a smaller "head" rectangle |
| `fabric_piece` | a small irregular four-sided polygon |
| `bundle` | a cluster of overlapping rectangles with a tie line across it |

A model trained on these learns to recognize **these specific shapes** — nothing about real fabric
texture, real tool shapes, or real lighting/clutter. A high score on the held-out synthetic test
split proves the shapes are easy to tell apart from each other; it says nothing about real-world
difficulty.

## Running it

```bash
python -m garment_cv.training.make_synthetic_dataset      # writes garment_cv/training/datasets/synthetic/
python -m garment_cv.training.train_synthetic              # ~30 epochs, GTX 1660 defaults (amp off)
```

The best checkpoint is copied to `garment_cv/models/synthetic_demo.pt`. Measured on the held-out
test split (420 images total, 300/60/60 train/val/test, YOLO11n, 30 epochs, ~20 minutes on a GTX
1660): **mAP50 0.977, mAP50-95 0.939** across all 7 classes — as expected for shapes this easy to
tell apart (solid colors, distinct silhouettes), not evidence of real-world detection difficulty.

To try it in the live app:

```
# garment_cv/configs/.env
GARMENT_DETECT_MODEL=garment_cv/models/synthetic_demo.pt
```

`ObjectDetector` reaches this through a real fallback, not a hack: `start()` checks whether the
loaded model's classes overlap at all with the COCO stand-in vocabulary (`person`/`scissors`/
`dining table`). A model that was going to be rejected outright before this change — this one has
*zero* overlap, since it only knows the 7 synthetic classes — is now recognized as a different kind
of model entirely, and `ObjectDetector` uses everything it offers instead of refusing to enable
detection (see `detector.py`'s module docstring and `ObjectDetector.start()`). Verified against a
real live server: `/api/status` reports `"custom_model": true` and the real 7-class list, and
`/api/detections`/the annotated stream correctly box and label real synthetic objects frame by
frame — not just a standalone inference script.

**Switch it back to `yolo11n.pt`** (or unset it) to return to real person/scissors/table detection
— the synthetic model can't detect those at all, since it was never trained on them.

## 2. AI-generated demo dataset

`prepare_real_dataset.py` turns 11 AI-generated images into a YOLO dataset, and `train_real.py`
fine-tunes on them. **These are not real photos.** They were generated by an image model, not
captured by any camera — confirmed by the images themselves: several show a tailoring workshop
(thread rack, mirror, pattern pieces) that doesn't exist at the real camera's location, every image
shares the exact same timestamp regardless of scene, and one shows two near-identical pairs of
scissors in the same frame, a known AI-image-generation artifact. Treat every detection this model
produces as "trained on a stylised impression of a tailoring scene," not "trained on your factory."

Classes (7, chosen to match what's actually visible across the 11 images — no `sewing_machine` or
`bundle` examples exist in this set): `person`, `fabric`, `scissors`, `marking_tool`,
`measuring_scale`, `pattern`, `fabric_piece`. Unlike the synthetic dataset, this one includes
`person` and `scissors` directly (rather than leaving them to the COCO stand-in) so a single custom
model can detect everything together — `ObjectDetector`'s custom-model fallback (see above) only
activates one model at a time, not a COCO-plus-custom blend.

Two real limitations beyond "it's AI-generated," worth being direct about:
- **Only 11 images, hand-labeled by visual inspection** (not drawn from a labeling tool) — boxes
  are reasonable, not pixel-perfect, and there's no meaningful held-out test split: `val`/`test`
  reuse the same 11 training images (not enough data to hold any back), so whatever metrics
  `train_real.py` prints are a fit check, not a generalisation measure.
- **Wrong room for the live camera.** The real camera (see the main `README.md`'s camera section)
  sees a different physical space entirely. A model trained only on these images is unlikely to
  detect anything reliably when pointed at the real live feed — test this directly before trusting
  it, don't assume it from the training-time numbers.

```bash
python -m garment_cv.training.prepare_real_dataset   # labels + copies the 11 source images
python -m garment_cv.training.train_real              # ~60 epochs, batch 4 (small dataset)
```

Best checkpoint: `garment_cv/models/real_demo.pt`. Same `GARMENT_DETECT_MODEL` swap-in as the
synthetic model above.

## 3. Real footage from the real camera

The first two datasets are fake (drawn shapes, AI-generated images). This one is not:
`capture_real_footage.py` grabs frames from the live camera while a person actually marks, cuts and
handles cloth, and `bootstrap_real_labels.py` turns them into a YOLO dataset. `train_live.py`
fine-tunes on it. Result: `garment_cv/models/live_demo.pt`.

```bash
python -m garment_cv.training.capture_real_footage --label cutting_action --seconds 10   # repeat per action
python -m garment_cv.training.bootstrap_real_labels                                      # draft labels -> dataset
python -m garment_cv.training.train_live                                                 # ~25 min on a GTX 1660
```

**What it is:** 83 labeled frames (58 train / 25 val), 5 classes (`person`, `fabric`, `scissors`,
`marking_tool`, `fabric_piece`), one ~15 minute session, one person cutting/marking, one table, one
camera angle. Validation mAP50 0.89 - but the validation frames are the *last 30% in time of each
clip from the same session*, so that number is optimistic. `measuring_scale`, `pattern`,
`sewing_machine` and `bundle` have no real examples and are not in this model.

**How labels were made (semi-automated, checked by eye in montages before training):** `person` from
the COCO model; scissors by colour (they're saturated orange); the cloth with one verified box per
action clip (automatic segmentation fails whenever hands touch it); the pen only in the clip where it
lies alone, because in-hand it's mostly hidden by fingers and a tiny box would be noise; the two
cloth pieces in the cloth-piece clip hand-placed (roughly +-30 px). A second person sitting further
back, too occluded for COCO to find, is added by a fixed box when a pink-clothing check says she's
there. Frames where someone else's arm reaches in were dropped rather than half-labeled.

**Settings that mattered, each learned from a failure:** `imgsz=1280` (the scissors and pen are only
60-150 px wide in a 2560 px frame - 15-40 px at 640), and `freeze=10` (the AI-image model forgot how
to detect even a clearly visible person after full fine-tuning; freezing the early backbone keeps the
general features).

**Measured on fresh footage it never saw:** found the seated person (0.96) and the cloth (0.95); did
**not** find orange scissors lying on top of cloth (never in the training clips - they were only
ever alone on the table or in a hand) and hedged between `fabric` and `fabric_piece` on a cut cloth
(the line between them is arbitrary for the same object). The fix for both is more varied footage,
not a different model.

To use it: `GARMENT_DETECT_MODEL=<absolute path>/live_demo.pt` and `GARMENT_DETECT_IMGSZ=1280`.

## When real data exists

Replace either dataset with one actually collected from a real garment production floor (spec
section 7's own list: varied workers, lighting, camera angles, fabric colors/patterns, tool sizes,
working speeds — plus explicit negative examples, like "worker holding scissors without cutting",
per section 7's cutting-dataset guidance). Neither training script needs structural changes beyond
pointing at the new dataset's yaml; the GTX 1660 training defaults (`amp=False`, `workers=2`) still
apply.
